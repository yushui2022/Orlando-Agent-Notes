# 术语、常见误解与自测

[学习目录](../README.md) · [官方资料](资料与版本口径.md)

## 在一句话里说清每个词

| 术语 | 本系列中的含义 | 易混点 |
|---|---|---|
| Producer | 产生并发布消息的程序 | send 返回不一定已到 Broker |
| Broker | 接收、保存、提供消息的服务端 | 不负责理解完整业务成功 |
| Consumer / Worker | 获取消息并处理的程序或实例 | 收到不等于处理成功 |
| Queue | 等待交付和确认的工作集合 | 多消费者通常分担工作 |
| Exchange / Binding | RabbitMQ 的路由实体与规则 | Exchange 不是任务结果数据库 |
| Topic | 逻辑类别；具体语义依产品而定 | Kafka topic 与 RabbitMQ topic exchange 不同 |
| Partition | Kafka 等系统中的分区日志 | 顺序范围通常是单分区 |
| Consumer group | 协同读取的一组消费者 | 独立订阅者要有独立进度 |
| Offset | 某个分区内的位置 | 不是跨分区全局消息 ID |
| ACK | 对某次投递的确认 | 发布确认与消费确认分开 |
| Outbox | 与业务数据同事务保存的发送意图 | 仍然可能重复发布 |
| Inbox | 消费端的处理记录或去重记录 | 必须与本地效果协调提交 |
| Idempotency | 重复执行不改变预期最终效果 | 不代表程序只被调用一次 |
| Lease | 一段时间内的领取或执行权 | 到期不会物理停止旧进程 |
| Fencing token | 资源侧用于拒绝过期执行者的令牌 | 只生成 token，不检查它，没有保护作用 |
| DLQ | 自动处理失败后的隔离位置 | 需要诊断、对账和受控回放 |
| Lag | 消费进度落后的量 | 不直接等于用户等待时间 |
| Backpressure | 把处理能力限制向上游传递 | 扩大缓存不等于背压 |
| Checkpoint | 可用于恢复步骤的持久记录 | 不自动撤销外部副作用 |

## 常见说法的适用边界

“用了 MQ 就解耦了”：实例位置与执行时间可以解耦，消息契约、数据依赖和可用容量仍然存在。

“同步接口无法扩容”：同步服务也可以增加实例和做负载均衡；MQ 提供的是独立排队、调度和恢复边界，不是唯一的并行手段。

“异步 HTTP 必然占满线程”：取决于运行时和编程方式。异步 I/O 可以提高等待并发，但没有自动提供持久任务恢复。

“ACK 后一定删除消息”：传统工作队列与日志模型不同；Kafka 提交位点通常不直接删除记录。RabbitMQ Streams 也不能简单套用普通队列的删除直觉。

“Consumer 不能超过 partition”：限定 Kafka 的常规消费组模型，不能套在所有产品和消费模式上。

“Kafka 完全不用 JVM 堆，零拷贝意味着没有复制”：这些是过度概括。页缓存和条件性的零拷贝路径减少成本，不会消除所有对象分配与数据处理。

“事务消息保证所有服务同时成功”：需要说明事务覆盖的资源。RocketMQ 事务消息不自动保证消费者外部业务效果与生产端原子提交。

“延迟消息、DLQ、事务支持打勾就能完成选型”：相同名称可能具有不同粒度、失败语义和版本约束。先写出业务要求，再核实目标版本。

## 自测题

先独立写答案，再展开参考思路。

<details>
<summary>1. 任务已入库，但 MQ 发送失败，应该回滚已经返回给用户的任务吗？</summary>

如果已经提交并对用户承诺接受，不能假设还能回滚过去的响应。应有持久发送意图与可重试发布，例如 Outbox；任务应保持可查询，长期发送失败需要告警和明确状态。
</details>

<details>
<summary>2. 相同消息重投三次，为什么生产者幂等还不够？</summary>

生产者幂等针对特定发布重试，不负责消费者执行的本地数据库或外部工具效果。消费者仍需业务幂等，尤其是处理完成后确认丢失的情况。
</details>

<details>
<summary>3. Kafka 一个分区的 11、12 已完成，10 还没完成，可否提交 13？</summary>

不能按“最大已完成位置”直接推进。那会越过尚未完成的 10，重启后可能跳过它。应跟踪连续完成区间，并结合实际已提交位置推进。
</details>

<details>
<summary>4. 进入速度 100/s，完成速度 80/s，多加一个很大的队列能解决吗？</summary>

只能暂时容纳增长。持续每秒积压 20 条，最终仍会耗尽容量或超出业务时效。需要提高有效处理能力、限制入口或减少工作量。
</details>

<details>
<summary>5. 旧 Worker 租约到期，是否可以确信它不再发邮件？</summary>

不能。进程可能仍存活。需要资源或工具网关验证执行权，以及外部操作幂等、结果查询或对账。数据库租约本身无法阻止任意外部请求。
</details>

<details>
<summary>6. 为什么不能先 SETNX event_id，再执行数据库业务？</summary>

标记成功后若业务失败，重投会被当作已处理。应使去重记录与本地业务效果同事务，或设计带状态、租约与恢复逻辑的处理协议；TTL 不是原子性的替代品。
</details>

<details>
<summary>7. 队列长度为零，能否证明用户任务全部完成？</summary>

不能。消息可能已交付但未确认，可能已被提前 ACK 并转交其他执行系统，也可能进入死信。需要查任务业务状态和整个交接链路。
</details>

<details>
<summary>8. 沙箱恢复到旧快照，能否把上传到对象存储的文件和已发送消息一起撤销？</summary>

通常不能。快照覆盖其约定范围内的状态，外部系统已经发生的副作用需要另外处理。应使用版本化产物、幂等操作和补偿或清理流程。
</details>

## 一次完整口头推演

用报告任务回答：为什么要排队、怎样可靠接受、消息在哪里保存、谁订阅、处理前后怎样确认、重复怎么处理、积压怎么算、取消怎么传播、执行怎么恢复。每个答案至少举一个失败时刻，并说出负责恢复的持久记录。这样得到的是能落地的设计说明，而不是孤立的术语清单。
