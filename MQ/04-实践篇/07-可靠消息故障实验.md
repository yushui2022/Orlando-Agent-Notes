# 07｜亲手制造四次崩溃

[← 上一篇](../03-进阶篇/06-Agent沙箱与消息系统选型.md) · [学习目录](../README.md) · [下一篇 →](08-RabbitMQ真实消息实验.md)

> 前置：第 03、04 篇；Python 3.11+。目标：让“会重复但不重复写业务结果”成为可以观察和断言的现象。

实验不调用模型，不创建沙箱，也不要求 Docker。我们用一个确定性的报告结果代替昂贵执行，把注意力放在事务提交和进程退出的相对位置。程序不是生产级 MQ，也不是 RabbitMQ 协议模拟器。

## 两个数据库，两个独立提交边界

代码位于 [reliable_queue.py](../实战/reliable_queue.py)。每个实验目录包含：

| 文件和表 | 保存什么 |
|---|---|
| `app.sqlite / tasks` | 已接受的任务和业务状态 |
| `app.sqlite / outbox` | 待发送的消息意图 |
| `app.sqlite / inbox` | 已完成的消费者与事件组合 |
| `app.sqlite / results` | 模拟报告结果 |
| `broker.sqlite / deliveries` | 每次发布产生的独立投递记录 |

故意使用两个文件，是为了不让消息发布和业务更新偷用同一个数据库事务。`relay` 向 broker 文件写入成功后，才更新 app 文件中的发送状态；`work` 提交 app 中的结果后，才确认 broker 中的投递。

Broker 模型领取消息时写入五秒租约和随机 receipt token。进程退出后，租约到期即可再次领取。这个机制用于教学；真实 RabbitMQ 的重投主要与未确认消息、连接或 channel 关闭等条件有关，不能把这里的“五秒”当成 RabbitMQ 默认行为。

## 准备目录和一次正常执行

下面使用 PowerShell，仓库按 G 盘路径放置。其他系统进入仓库的 `MQ/实战` 目录后，Python 命令相同。

```powershell
Set-Location 'G:\Projects\Orlando-Agent-Notes\MQ\实战'
$env:PYTHONDONTWRITEBYTECODE = '1'
python --version
python reliable_queue.py --data .data/normal submit t1 "first report"
python reliable_queue.py --data .data/normal relay
python reliable_queue.py --data .data/normal --now 0 work
python reliable_queue.py --data .data/normal status
```

预期 `work` 返回 `succeeded`；任务状态是 `succeeded`，results 和 inbox 各一条，投递状态是 `acked`。相同参数再次 submit 会返回原来的事件标识，不创建第二个任务；相同任务编号改成不同标题会报错。

`--now` 是逻辑时间，用来推进实验，不会修改系统时钟。一个实验中始终使用这一时间口径；省略时程序使用真实时间。每个案例使用新的目录名，重复运行同一案例前也换一个新目录，避免旧状态影响现象。

## 崩溃一：消息发出，尚未记录发送成功

```powershell
python reliable_queue.py --data .data/crash-publish submit t1 "report"
python reliable_queue.py --data .data/crash-publish relay --crash after-publish
$LASTEXITCODE
python reliable_queue.py --data .data/crash-publish status
python reliable_queue.py --data .data/crash-publish relay
python reliable_queue.py --data .data/crash-publish --now 0 work
python reliable_queue.py --data .data/crash-publish --now 0 work
python reliable_queue.py --data .data/crash-publish status
```

带 `--crash` 的命令预期退出码为 **86**，表示在指定位置直接退出进程。第一次 status 应看到 Broker 已有投递，但 outbox 的 sent 仍为 0。再次 relay 后，Broker 中有两份同事件的投递。两次 work 分别返回 `succeeded` 和 `duplicate`，最终只有一条结果。

这证明了 Outbox 发布存在重复窗口，同时展示消费者如何承受这个窗口。不要把“出现两份投递”当成实验失败；真正的断言是两份投递没有产生两份业务效果。

## 崩溃二：已经领取，尚未开始写结果

```powershell
python reliable_queue.py --data .data/crash-claim submit t1 "report"
python reliable_queue.py --data .data/crash-claim relay
python reliable_queue.py --data .data/crash-claim --now 0 work --crash after-claim
python reliable_queue.py --data .data/crash-claim --now 4 work
python reliable_queue.py --data .data/crash-claim --now 5 work
```

时间 4 时返回 `empty`，因为租约尚未过期；时间 5 时重新领取并返回 `succeeded`。领取消息并不等于完成消息，接管机制必须知道哪些工作仍未完成。

## 崩溃三：结果已写入事务，但尚未提交

```powershell
python reliable_queue.py --data .data/crash-transaction submit t1 "report"
python reliable_queue.py --data .data/crash-transaction relay
python reliable_queue.py --data .data/crash-transaction --now 0 work --crash before-commit
python reliable_queue.py --data .data/crash-transaction status
python reliable_queue.py --data .data/crash-transaction --now 5 work
```

崩溃后第一次 status 中，inbox 和 results 都应为空，任务仍是 queued。代码使用 `os._exit(86)`，绕过 Python 的 `finally`，由 SQLite 的事务恢复处理未提交修改。这比仅仅抛出异常再执行主动 rollback 更接近进程突然消失。

到时间 5 再次处理，inbox、results 和任务状态一起提交成功。若去重记录被单独提前提交，此处就会把没有结果的任务误判为已完成。

## 崩溃四：结果已经提交，尚未 ACK

```powershell
python reliable_queue.py --data .data/crash-ack submit t1 "report"
python reliable_queue.py --data .data/crash-ack relay
python reliable_queue.py --data .data/crash-ack --now 0 work --crash after-commit
python reliable_queue.py --data .data/crash-ack status
python reliable_queue.py --data .data/crash-ack --now 5 work
python reliable_queue.py --data .data/crash-ack status
```

中间状态应同时出现“结果已存在”和“投递仍为 inflight”。这不是矛盾，而是两个系统掌握的信息暂时不同。时间 5 的 work 应返回 `duplicate`，随后投递变成 acked，结果数量不变。

## 持续失败：退避与死信

```powershell
python reliable_queue.py --data .data/poison submit t1 "report"
python reliable_queue.py --data .data/poison relay
python reliable_queue.py --data .data/poison --now 0 work --fail
python reliable_queue.py --data .data/poison --now 0.5 work
python reliable_queue.py --data .data/poison --now 1 work --fail
python reliable_queue.py --data .data/poison --now 3 work --fail
python reliable_queue.py --data .data/poison status
```

预期依次为 `retry、empty、retry、dead`。失败并没有产生报告结果。教学模型使用确定性的 1 秒、2 秒退避以便断言，生产中还应加入随机扰动和截止时间。

此模型中 dead 状态与任务 failed 状态分属两个数据库，不是原子提交。若在两者之间崩溃，需要额外对账修复。实验没有覆盖这个窗口，也没有实现完整生产死信恢复，不能从前四个测试推断“所有故障都已解决”。

## 自动断言比肉眼看日志更可靠

```powershell
python -m unittest discover -v
```

这会运行 13 项测试：9 项针对本地队列模型，4 项针对下一篇 RabbitMQ 消费者的本地业务处理函数。测试会创建独立临时目录，并启动子进程制造四种崩溃；测试数据默认位于当前 G 盘项目的 `.test-tmp/`，每次测试后清理。

验证范围包括重复提交、Outbox 恢复、重复发布、未提交事务回滚、提交后重投、退避、终止重试和旧 receipt 不能确认新投递。它**不验证**网络分区、Broker 复制、整机断电、真正沙箱执行或第三方 API 的幂等。

旧 receipt 测试只保护 Broker 确认。它不代表旧 Worker 无法操作外部资源；第 06 篇讨论的执行 epoch 与资源侧检查仍是另一层能力。

## 做一次自己的变体

复制一份实验代码到单独练习目录，把 `work` 中的 ACK 移到业务事务之前，再制造 after-claim 之后的崩溃。写下你预计哪张表会缺记录，然后实际观察。这道练习的价值在于从事务边界推导结果，而不是记住“先处理后 ACK”这句口号。
