# 05｜顺序、重试、积压：系统变忙以后怎么办

[← 上一篇](../02-入门篇/04-Outbox幂等与事务.md) · [学习目录](../README.md) · [下一篇 →](06-Agent沙箱与消息系统选型.md)

> 前置：第 03、04 篇。目标：遇到乱序、反复失败和积压时，能按业务约束选择处理策略。

小规模实验里，每个任务都很快，消息总按预期完成。真正的 Agent 工作负载却常常长短不一：有的资料几秒钟读完，有的模型调用等待一分钟，有的沙箱安装依赖失败后再次尝试。同一套投递机制开始面对不均匀的执行时间。

## 先分清三种顺序

生产者写入顺序、消费者收到顺序、业务完成顺序是三件事。一个队列可以先交付 A 再交付 B，但两个 Worker 并行处理时 B 先完成。对 Kafka 分区也一样：顺序读取后扔进线程池，线程池不自动按读取顺序完成。

假设同一任务依次产生 `Started、ArtifactUploaded、Completed`。如果完成事件先处理，系统却还没有可下载文件，用户会看到一个错误的成功状态。解决方法要从业务要求选择：同一任务串行处理，或者让状态更新带版本检查、允许暂存等待缺失前置。

| 要求 | 可能的设计 | 需要接受的代价 |
|---|---|---|
| 同一任务严格顺序 | 按 task_id 分区，任务内串行，失败时阻塞该顺序流 | 慢任务或坏消息可能阻塞后续 |
| 只关心最新状态快照 | 带单调版本号，条件更新 | 必须确认中间版本可跳过 |
| 每一步都有不可省略效果 | 显式状态机，缺前置时等待或补齐 | 状态和恢复逻辑更多 |
| 全局严格顺序 | 一个全局序列化协调点 | 并行度和可用性受限 |

版本号也不是万能药。余额“增加 10 元”是增量事件，不能因为收到更高版本就随意丢弃低版本；“余额快照为 100 元”才可能按最新版本覆盖。先弄清消息表达的是增量还是快照。

普通消费组发生 rebalance 并不自动意味着分区日志顺序改变。风险常在应用侧：旧消费者仍有未完成工作，新消费者已经开始处理；或应用错误提交了超过未完成记录的位点。撤销分区时处理在途工作、限制并发并正确提交进度，才是在控制这个窗口。

## 重试之前，先给失败分类

网络抖动、短暂限流可能稍后恢复；缺少必需字段、输入已被永久删除、用户已取消任务，通常不能靠反复执行解决。相同异常消息立刻重新入队，会形成高速循环，占满网络和 Worker，却没有增加任何成功结果。

一个示例策略是最多尝试 3 次，间隔 1 秒、2 秒，仍失败进入死信或隔离流程。生产中常用指数退避加随机扰动，避免一批 Worker 同时恢复、同时再次打满下游：

```text
最大等待 = min(上限, 基础间隔 × 2^(重试序号 - 1))
实际等待 = 在 0 到最大等待之间随机取值
```

重试策略还要受任务截止时间约束。报告一分钟后就没有业务价值，即使“还剩三次重试”也不该继续排队一小时。对模型 API 的限流应结合服务方提示和全局配额，不能让每个 Worker 自己盲目重试。

## 重试会改变顺序，也会增加负载

如果 A 失败后送入延迟重试队列，主队列中的 B、C 会继续完成。当业务要求 A→B→C 时，这种方案会破坏预期。可以选择阻塞该任务的后续消息，或者让编排器把依赖关系记录下来，等 A 成功才释放 B。

多层重试还可能相乘。假设 MQ 最多投递 3 次，每次 Worker 调用模型最多尝试 3 次，最坏会有 9 次调用。若沙箱内脚本自己又重试，成本继续放大。要明确谁拥有重试策略，并记录逻辑尝试与传输重投的区别。

第 07 篇的教学模型把尝试次数记在投递记录上，足以观察退避；生产任务预算通常还要按稳定 `task_id` 计数，防止重复发布让预算重新开始。

## 死信队列需要后续处理

消息进入 DLQ，说明自动处理路径停下了。它不等于业务完成，也不等于问题已经解决。记录中应能找到原消息标识、失败分类、次数、首末失败时间、任务和租户，以及负责处理的人或服务。

修复后回放要保留业务幂等标识，并控制速度。若原任务已取消、输入版本已失效或权限已撤销，应先重新判断是否允许执行。批量把所有死信倒回主队列，可能把已修好的系统再次压垮。

RabbitMQ 的 DLX 是把符合条件的消息重新路由到其他交换机；默认死信转发与配置为至少一次的死信转发，可靠性边界不同。不要仅仅声明了 DLQ 就认为转发绝不丢失。具体条件见 [RabbitMQ 4.1 Dead Letter Exchanges](https://www.rabbitmq.com/docs/4.1/dlx)。

## 用数字判断积压能不能消完

令进入速度为 λ，平均完成速度为 μ，当前积压为 B。当 λ、μ 在一段时间内近似稳定且 μ > λ 时，清空积压的粗略时间为：

```text
清空时间 ≈ B / (μ - λ)
```

假设 8 个 Worker，每个同时只跑一个任务，平均任务耗时 20 秒；忽略其他瓶颈时，总处理能力约为 `8 / 20 = 0.4 个/秒`。持续到达速度为 `0.25 个/秒`，积压为 300 个，那么清空时间约为 `300 / (0.4 - 0.25) = 2000 秒`，约 33 分钟。

这只是容量估算。Agent 耗时有长尾，模型 API 有并发和 token 限制，沙箱也有资源上限，实际 μ 未必随着 Worker 数量线性增长。如果每个任务要调用工具 5 次，工具配额只有每秒 1 次，理论上该工具已把吞吐限制到约每秒 0.2 个任务。

稳定系统还可以用 Little 定律理解在途数量：平均在途任务数约等于到达速度乘平均端到端停留时间。排队时间、执行时间的边界要一致，不能把一个系统的到达率乘另一个阶段的耗时。

## 监控不要只画一个队列长度

| 指标 | 帮你发现什么 |
|---|---|
| 最老待处理消息年龄 | 用户实际等了多久；少量长任务也可能超时 |
| 进入率与完成率 | 积压是暂时波动还是持续增长 |
| ready 与 unacked 数量 | 是没被领取，还是已领取但执行缓慢 |
| 处理耗时 p50/p95/p99 | 是否被少数长任务拖慢 |
| 重试、死信与失败分类 | 是否正在产生无效工作 |
| 每个分区或业务 key 的负载 | 热点是否被总体平均值掩盖 |
| 下游限流、连接池、CPU/内存 | 增加消费者是否只会进一步争抢资源 |

排查时先比较流入和完成速度，再沿任务追踪慢在哪个阶段。消息只是被快速搬进另一个内存线程池时，Broker 的 lag 可能很好看，真正的待办却藏在 Worker 内存里；进程重启还可能丢掉它们。不要靠提前 ACK 来改善监控数字。

## 限流和公平比无限扩容更早到来

对于 Agent 平台，一个租户提交十万份报告，不应挤掉所有其他租户。可以按租户限制排队额度、并发和预算，再给短任务与长任务划分不同资源池。具体队列数和调度算法取决于规模，不能简单为每个用户无限创建队列。

负载超过可处理上限时，入口应返回明确的限流或稍后重试信号。已经接受的任务要保持可查询；尚未可靠接受的请求不能返回成功。下一篇把这些规则放进包括模型、工具和沙箱的完整执行链路。
